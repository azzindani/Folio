# Live sweep #17 — turning last pass's luck into an audit

Pass 16 ended on an observation: the productive question is not "is this op
correct?" but **"which of its siblings never got told?"** It had found three
faults that way, all by accident. Pass 17 stops relying on accident: enumerate a
careful behaviour, then check every op that should have it.

## Invariant 1 — can you find a layer inside a group?

267 of 279 designs on the server contain a group, so this is not an edge case.
Probing one group child, `st_grain`:

| op | reaches it |
|---|---|
| `update` | ✓ |
| `align` | ✓ (fixed pass 16) |
| `split_text` | ✓ |
| `animation keyframe` | ✓ |
| **`remove`** | ✗ *"Layer not found: st_grain"* |
| **`templates save_component`** | ✗ *"No matching layers for IDs"* |

The same id meant different things depending on which door you used — and one of
the two blind ops is the destructive one.

## Invariant 2 — the carousel guard

`pagesWithLayer` exists to stop an unscoped edit hitting every page. Its own
comment calls it "the silent-nuke footgun". It asked only about **top-level**
ids, while every op it guards recurses into groups — and carousel pages are
built from the same presets, so their group CHILDREN share ids exactly as their
groups do.

On a 3-page deck:

    edit_layer {op:"update", layer_id:"st_grain", props:{opacity:0.123}}
      reply: updated: st_grain      ← one layer
      file:  3 pages changed

Precisely the corruption the guard was written to prevent, through the door it
never watched. This is the most serious find of the pass.

## Invariant 3 — does `locked` protect anything?

| op | honours a locked ancestor |
|---|---|
| `update` | ✓ refuses, names the group |
| `align` | ✓ skips + reports |
| `remove` | ✓ (added here, with the recursion) |
| `split_text` | ✗ |
| `keyframe` | ✗ |
| `motion` | ✗ |
| `patch_spec` | ✗ |

**Not shipped, deliberately.** I first read this as four ops ignoring a user's
"do not touch". Then I read what sets the flag: `locked: true` is authored by the
MODEL, and the guide actively tells it to wrap a hand-placed composition in
`{type:"group", locked:true, …}` so the auto-rescue passes leave the geometry
alone. **248 of 276 library designs do exactly that.** Its documented meaning is
"the rescue passes must not reflow this", not "no tool may ever touch it".

Making `split_text` refuse would therefore stop headline splitting from working
on nearly every real design — a regression dressed as a fix. Whether `locked`
should also gate explicit edits is a product decision. Recorded, not decided.

## What shipped

One lookup, `engine/layer-lookup.ts`, used by all of them: `findDeep`,
`scopesWithLayer`, `lockedAncestorOf`, `removeDeep`, `parentIdOf`. `remove`
descends and respects a locked group (descending without that check would have
made `locked` weaker than before). The component instance returns to the group
its originals came from rather than being hoisted to the top level, which would
move it in the composition. `save_component` names ids it could not find.

17 tests on the module, 4335 in the suite.

## Two more, found while VERIFYING the fixes

Deploy-and-check turned up as much as the audit did.

**`patch_spec` silently drops `locked`.** Verifying the `remove` fix, the group
I had locked minutes earlier was unlocked. Not a mystery — `patch_spec`
re-expands the preset and replaces the whole layer, and `locked` is not part of
any spec, so it goes with it. Measured: `locked` before 1, after 0.

Note this is the OPPOSITE call from invariant 3 above, and for a good reason.
There the question was whether an op should REFUSE on a locked ancestor —
arguable, load-bearing, left alone. Here an unrelated edit ERASES the flag, so
the composition silently rejoins the reflow it opted out of. Nothing is arguable
about that. `locked` and `href` now survive the rebuild.

**My own snapshot fix from pass 16 had a latent ordering bug.**
`snapshotsNewestFirst` sorted by mtime — milliseconds — and a small design
snapshots faster than that. The tie made "newest" arbitrary, so the
unchanged-file check compared against the wrong content and duplicated anyway.
It passed alone and failed only in a full run, where three writes shared a
millisecond. Ordering is by NAME now: the name carries an ISO timestamp plus a
collision counter, so it is both unique and chronological.

Worth stating plainly: a fix shipped one commit earlier was wrong in a way its
own passing test could not see. The full suite caught it because the timing
changed.

## Across seventeen passes

| Pass | Faults |
|---|---|
| 1–11 | 21 |
| 12 | 0 |
| 13 | 1 |
| 14 | 2 |
| 15 | 2 |
| 16 | 3 |
| 17 | 5 shipped + 1 reported |

36 faults, 23 commits. The method converged: pass 16 noticed that siblings drift
apart, pass 17 made that a checklist — pick an invariant, list every op that
could break it, probe them all live. Two of three invariants had holes. The
third turned out to be a case where the "inconsistency" was load-bearing, which
is the reason to check what a flag MEANS before enforcing it everywhere.

And the last two came from **verifying**, not from searching: one because a lock
I had set had quietly vanished, one because the full suite ran the same test at
a different speed. Neither would have been found by a cleverer probe. The habit
that pays is checking the thing you just fixed, on the running server, and
looking at what else moved.
