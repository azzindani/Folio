# Live sweep #23 — does the engine measure text it has never been asked to measure?

Twenty-two passes probed the engine's machinery. This one goes at its core
promise. CLAUDE.md §0.4: *"Spatial correctness is the engine's job."* Every
layout decision — fit, overflow, stacking, the box a preset gives a paragraph —
rests on one estimate: how tall will this text render?

So hand it text nobody has handed it before.

## Three scripts, one 700×120 box at 32px

| | declared | engine measured | ink rendered |
|---|---|---|---|
| Latin | 120 | **208** (grew, 5 lines) | y 58..272, x 50..749 — inside the box |
| **CJK** | 120 | **84** (SHRANK, 2 lines) | y 53..87, **x 55..799** |
| emoji | 120 | 125 | inside the box |

The CJK box is 800px wide. The text ran to **x=799** — off its 700px box, off
the canvas, clipped. One line, never wrapped.

And then:

    diagnose_design → "No problems — some polish suggestions."
                      errors: 0   warnings: 0

## Why

Two independent pieces of arithmetic, both wrong the same way.

`wrapPlainText` (renderer) splits on `' '` and compares `.length` against
chars-per-line. **CJK has no spaces**, so a 66-glyph paragraph arrives as ONE
token and is pushed out as a single line. Nothing breaks it. A long URL has the
same shape.

`estTextHeight` (engine) counts `seg.length` — UTF-16 code units — at a flat
0.54 em. A Han glyph renders at 1 em, so 66 of them were measured as if they
were 34: two lines, 84px. That is why the engine *shrank the model's declared
120px box* — it believed the text needed less room than the model had given it.

An astral emoji is the mirror image: `'🎯'.length === 2`, so it was charged
double.

`diagnose_design` uses the same estimator, so **the instrument shared the bug
with the thing it was measuring.** That is why 4,400 unit tests and twenty-two
sweeps never saw it.

## Fixed in one place, not two

`utils/text-width.ts` now owns the width class (full-width for CJK / Kana /
Hangul / fullwidth forms, iterating code POINTS) and `wrapToWidth` — the single
line-breaking implementation. The renderer calls it. `estTextHeight` calls it
and counts the lines that will actually be drawn.

My first attempt fixed both sides *separately* and they still disagreed: the
estimator divided total width by line width, which assumes perfect packing, so
it under-counted whenever a token could not break where the arithmetic wanted —
5 lines estimated against 6 rendered. **Two rules that agree on average is
exactly the failure being fixed.** Sharing one implementation makes the test an
exact equality instead of a tolerance.

Mid-token breaking is a last resort, so a long URL now wraps instead of bleeding
off the page. Plain Latin wraps exactly where it always did — asserted against a
reproduction of the original algorithm, so the regression guard does not depend
on my reading of it.

## And then the fix didn't work

Deployed it, rebuilt the CJK case live, and the engine still measured 84px.

There were **three** implementations of one rule, not two:

| where | signature | used by |
|---|---|---|
| `renderer/layer-renderers-shared` | `wrapPlainText` | draws the lines |
| `mcp/engine/text-measure` | `estTextHeight(…, font?: string)` | diagnose_design |
| `mcp/shorthand-helpers` | `estTextHeight(…, charFactor = 0.54)` | **the presets + finalize passes** |

Same name, same job, different file, different fifth argument. The pass that
actually sets a text layer's height imports it from `shorthand-parser` — so
fixing the other two changed nothing about what the engine does. Ten modules
hang off that third one, including every preset.

It had already been taught half this lesson. Its own comment says a char-count
estimate under-counts lines, so it "greedily packs words exactly as the renderer
does". **Re-implementing the renderer is how copies drift** — it still charged
every UTF-16 code unit the same advance.

All three now call `wrapToWidth`, and the test asserts the three-way agreement
directly so a fourth copy cannot appear quietly.

**This is the strongest argument yet for finishing the chain.** The bug was
found live, fixed with tests, CI-green, and *still wrong* — and only deploying
and re-running the original measurement showed it. A green suite proved nothing
here, because the suite tested the copy I had already fixed.

## Verified live, after deploying

Same brief, same 700×120 box at 32px (the paragraph is 62 glyphs, not the 66 I
first counted — 62 × 1 em ÷ 700px = 3 lines):

| | before | after |
|---|---|---|
| engine height | **84** (shrank the model's 120) | **125** (grew it — 3 × 41.6) |
| rendered lines | 1 | 3 |
| ink | x 55..**799**, clipped by the canvas | x 55..485, inside the 700px box |
| `diagnose_design` | "No problems — 0 errors" | *see below* |

Renderer, `diagnose_design` and the preset estimator all answer 125 for this
text — the number the live server stored. The third check is the one that
matters most, so it was run against the design built by the *broken* engine,
whose box really is 84px:

    error  text_overflow  text "t" (32px) wraps to ~3 lines (~125px) but its
                          box is only 84px tall — it spills ~41px past the box

The instrument now sees the exact defect it was blind to.

(The export image has no CJK font, so the glyphs render as tofu. That is
environmental, and the tofu advance is ~0.64 em where a real Han glyph is 1.0 —
which is why the ink stops at 485 rather than ~722. Geometry was what was under
test; the font is a separate matter.)

## A third fault, found in the cleanup

Binning the sweep project turned up **81 of 371 cached thumbnails belonging to
projects that no longer existed.**

A thumb is `<project>__<file>.<fingerprint>.png` in one flat directory, so the
project name is in the FILEname and does not move when the folder does.
`deleteFolder` renames the directory into `.trash`; `renameFolder` renames it in
place. Both are correct about the directory and silent about the cache.

Pass 19 gave the library a pruner — but it prunes one *design's* older renderer
generations. Nothing ever pruned by project, because the two ops that delete and
rename projects called nothing at all. **The capability was there; the door was
not** — the session's dominant bug class, one more time, found by using the
product rather than by reading it.

Rename is the worse half: the old set is stranded under a prefix nothing will
ask for again *and* every thumbnail is re-rendered under the new one, though a
rename changes no design's bytes. Both ops are wired now, and the two tests that
assert the wiring fail against the previous code.

Passes 19–22 each compared two things that must agree: two artefacts, two
moments, an input against itself, an output fed back as input. This one is the
same move aimed outward rather than inward — compare the engine's *claim* about
the world against the world. It reported "No problems" about a design whose
text was off the canvas, and it did so honestly, because the number it checks
against is the number it got wrong.

**A measurement and the thing it measures must not share an implementation of
the mistake.**
