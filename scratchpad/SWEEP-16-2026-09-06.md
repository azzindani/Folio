# Live sweep #16 — what does a FAILED call leave behind?

Pass 15 asked whether an operation returns you to where you were. Pass 16 asks
the question underneath it, which nobody had: **when a call fails partway, does
it leave the design as it found it?** Every tool implicitly promises that, and a
partial write on a failed call is silent corruption.

## Atomicity holds

Byte-diffing the design after each call that must fail:

| call | result |
|---|---|
| `add_layers` — 2 good layers, 3rd invalid | rejects the whole batch, **unchanged** |
| `remove` a layer that does not exist | clean error, **unchanged** |
| `shape` on a missing layer | clean error, **unchanged** |
| `split_text` on a rect | *"r1 is a rect, not text"*, **unchanged** |
| `themes apply` unknown theme | clean error, **unchanged** |
| `resize` to a refused size | clean error, **unchanged** |
| `patch_design` — 1 good selector, 2 bad | applies 1, names both in `unresolved` |

`patch_design` is the model to copy: a batch op that applies what it can and
says exactly what it could not.

## Three that did not

### 1. align could not see inside a group

    edit_layer {op:"align", layer_ids:["st_bg","st_stat"]}
      -> "No positioned target layers found."
    edit_layer {op:"update", layer_id:"st_stat", …}
      -> success

`update` recurses into groups, with a comment saying why: *"every MCP poster is
ONE group"*. `align` scanned only the page's top level. On the server, **267 of
279 designs contain a group** — so align was unusable for the inner layers of
virtually every real design, and said so in a way that reads like the caller's
mistake.

### 2. align silently dropped ids that do not exist

    layer_ids: ["r1","r2","ghost"]
      -> success: true,  aligned: ["r1","r2"]
      -> no `unresolved`, no `skipped`, no note, no warning

The caller had to diff the arrays it sent against the array it got back to
notice. Fixed to `patch_design`'s convention, plus a `skipped_locked` for a
child left alone because its group is locked — which the recursion made possible
to get wrong, so it is now explicitly right.

### 3. A failed call ate the undo history

Ops snapshot BEFORE validating, so a call that fails still wrote a `.bak`
byte-identical to the previous one. Retention is capped at 20. Measured live:

    snapshots: 19
    12 × update on a layer id that does not exist   (design never changed)
    -> the three OLDEST restore points: EVICTED

History destroyed by operations that did nothing. `snapshot()` now hands back
the newest existing one when the file is unchanged — fixed there rather than by
moving the call after validation in every op, because those are exactly the ones
nobody would remember to change.

## Note on scope

`align` moved to `engine-align-tools.ts`; `engine-export-tools.ts` was over the
700-line ceiling and aligning layers is a geometry edit, not an export. Same
split the file's own footer describes for `batch_create`.

## Across sixteen passes

| Pass | Faults |
|---|---|
| 1–11 | 21 |
| 12 | 0 |
| 13 | 1 |
| 14 | 2 |
| 15 | 2 |
| 16 | 3 |

31 faults, 21 commits. The three here share one shape with pass 14's `move`: a
lesson learned by one op and never carried to its sibling. `update` learned to
descend into groups; `align` did not. `patch_design` learned to report what it
skipped; `align` did not. `delete` learned to maintain the manifest; `move` did
not. **The question that keeps paying is not "is this op correct?" but "which of
its siblings never got told?"**
