# Live sweep #24 — when the engine refuses, is its advice true?

Twenty-three passes tested what the engine **does**. This one tests what it
**says to do**. A blind model has no other recourse: when a call fails, the
`hint` is the entire path back. So take the hints literally, do exactly what
each one says, and see whether the next call works.

The surface: 235 `errResult` sites, 109 `hint:` fields, 83 `next_action`s.

## Most of it is true

| claim | check | verdict |
|---|---|---|
| unknown tool → "Available: …" (21 names) | diffed against `tools/list` | exact, both ways |
| unknown op → "Set op to one of: …" | called all **68** named ops | every one dispatched |
| "use inspect to find layer IDs — group children are listed with a parent field" | inspected a real 8-page deck with `page_id` | true: children flattened, `parent` set |

That third one I first recorded as a lie, because inspect showed me no children
at all. It was my own input: I had authored the group with the wrong key. **The
instrument again** — the fourth time in six passes. Re-tested with a canonical
group and it works exactly as promised.

But the wrong key turned out to be the finding.

## `children:` — the word every other scene graph uses

Folio's schema says a group holds `layers: Layer[]`. `children` is what Figma,
SVG-adjacent tooling and React all call it, so it is what a model reaches for.
Nothing in Folio read it. Live, on an 1080×1350 poster, two text layers in two
groups:

```
add_layers      → success: true, added: 3
next_action     → "Layers added. Call seal_design."
findDeep        → descends `layers` — every child "Layer not found"
inspect         → the group, no children
the renderer    → threw, drew a dashed  ⚠ group#locked_block  placeholder
diagnose_design → "No problems — 0 errors, 0 warnings"
```

The content went in and an empty warning box came out, and the reply advised
sealing it. Every recovery route the model has was a dead end, and the one that
spoke ("Layer not found") was technically true and useless — the layer is right
there in the file.

The renderer's caught message was `Spread syntax requires ...iterable not be
null or undefined`.

## The general fix is the second one

Folding `children` → `layers` on ingest fixes this instance. It sits beside
`normalizeTextAliases` in the same chain of alias-folding rescue passes that
already recovers half a dozen plausible model shapes, and it has to run before
everything that recurses, because all of them look for `layers`. §0.4 says fold
rather than reject: the model's authoring should work, not be corrected.

But the deeper gap is that **nothing asked whether the design renders**. Every
check in `diagnose.ts` reasons about the spec, so all of them can pass while a
layer throws on the way to the canvas. The renderer already knew — it catches,
draws the placeholder, and records `data-render-error` on the group. Nobody read
it.

`diagnose-render.ts` asks the renderer instead of re-deriving its answer, which
is the pass-23 lesson pointed the other way: **not sharing an implementation is
what let them disagree; here, not consulting one at all is what let the
diagnosis be wrong.** It also makes the check open-ended — any layer that fails
to draw, for any reason introduced later, is a finding without this file
knowing why.

## Two more false hints

**A paged design's summary inspect names no layer ids and offers no
next_action.** Each page is one group, so `layer_count` reads 1 and there is
nothing to act on. A model whose edit just failed is told "use inspect to find
layer IDs" — and inspect, at the level it naturally calls it, shows none. It now
points at `page_id`, which does flatten the group.

**An unknown op was answered by the argument guard, not the multiplexer.**
`edit_layer {op:"bogus"}` came back `needs 'design_path'` — true, and advice for
a call that fails again, since supplying it gets you "Unknown op" anyway. The
guard now defers when the op is not real. Doing that required the op lists to
become data: they were literals inside eight `default:` branches, and
`required-args.test.ts` had been recovering them with a **regex over
dispatch.ts's source** — an audit that reformatting could have silently emptied.

Passes 19–23 each compared two things that must agree. This one compares the
engine's *instructions* against the engine's *behaviour* — and the instructions
were, overwhelmingly, honest. What they could not describe was a shape the
engine never considered, where four separate surfaces each answered correctly
about the thing they could see and the model was told, in sum, something false.

**Advice is a door too, and a true statement can still be the wrong one to
make.**
