# Live sweep #19 — is the picture the model approves the file the user gets?

Eighteen passes checked what the engine does and what the guide says. This one
checks something neither covers: the model iterates on `render_preview`, the
user receives `export_design`. If those two disagree, every design in the
library was signed off against something other than the deliverable.

## They agree

| comparison | result |
|---|---|
| preview vs PNG export @1 | **byte-identical** (97,319 bytes both) |
| preview vs PNG export @2 | **byte-identical** (2160×2700) |
| carousel page 1/2/3 vs deck-p1/p2/p3.png | **identical**, and correctly ordered |
| PDF (vector, separate path) | selectable text, landmarks within 1–2px of the PNG |
| SVG | all content present |

The PDF deserves a note: it is a real vector file — `pdftotext` pulls back
FIDELITY / the body copy / TONNAGE / 7.97M / "Source: sweep 19", 24 embedded
font objects — and rasterised at 96dpi its orange landmarks sit at y 597..739
against the PNG's 596..739. That is rasteriser antialiasing, not layout drift.

## What comparing them turned up

The exported SVG defines a filter that nothing uses:

    <filter id="noise-11"><feTurbulence …/></filter>     ← defined
    filter="url(#noise-11)"                              ← 0 occurrences
    <rect … fill="none" data-layer-id="s_grain"/>        ← paints nothing

A `noise` fill paints nothing on the shape itself. `applyFill` returns
`fill:'none'` plus a SIBLING rect carrying the turbulence filter, which the
caller has to place. **Only the layout renderer ever did.**
`renderRect`/`Circle`/`Path`/`Polygon` read `.fill` and dropped
`.extraElements`.

The engine's own background composer emits exactly that shape for a grain
sweep — `{id:"…_grain", type:"rect", fill:{type:"noise"}}` — so **22 of 276
library designs carry a grain nobody has ever seen**, and every SVG export of
one ships a dead filter def.

The single working caller was wrong too, in the opposite direction: the noise
rect is built at 0,0 with the box's width/height, so appending it to a container
at (80,780) grained the top-left of the canvas rather than the container. Bounds
now carry an origin.

Wrapping happens only when there is something to add, so every other shape's
output is unchanged — asserted in a test, not assumed. Six of the seven new
tests fail without the fix; the seventh is the one that must keep passing.

## The second fault: verifying the first one found it

Deploying the noise fix, I re-exported the very design that had exposed it.
Byte-identical output, dead filter still there:

    "reused": true,
    "note": "Nothing was re-rendered: this design has not changed since it
             was last exported to this path at this scale…"

The export cache keys on `(design bytes, format, scale, destination)` — and
`export-receipt.ts` calls that "the whole claim" in its own doc comment. It is
one term short. **An export is also a function of the code that renders it**,
so a renderer fix reaches no design that was already exported. The cache serves
pre-fix bytes for ever, says `reused: true`, and is telling the truth as it
understands it: the design really has not changed.

The grain fix would therefore have been invisible on exactly the designs that
needed it — the ones already exported once.

Fixed by folding a hash of `renderer/` + `export/` + `engine/` sources plus the
dependency versions into the key. Hashing sources rather than bumping a version
constant is the whole point: nothing to remember, so nothing to forget. Folded
in INSIDE `exportKey`, not passed by the caller, so no future call site can key
an export on the design alone.

Blast radius here is small — 11 cached entries across 6 of 279 designs — but the
cap was permanent and applied to every renderer fix that will ever ship.

**Two fixes, one lesson: the reuse path is a door.** A cache that keys on the
input and not the transform is the same species as a guard that keys on the
tool and not the op.

## Two false starts worth recording

- The SVG is **2,199 bytes** against a 97KB PNG and a 284KB PDF. I read that as
  content missing. It is not — vector output is simply compact, and every
  element was there. Looking before concluding is what turned a wrong hunch
  into the real finding two lines later.
- I checked the PDF for text by decompressing streams by hand and found none,
  which would have suggested the text was outlined to paths. `pdftotext` was
  installed the whole time and showed the text immediately. **Use the real tool
  before believing a hand-rolled probe.**

39 faults, 26 commits. This pass is the strongest evidence yet for the method
that has carried the last ten: **compare two artefacts that must agree.** The
two agreed — and the comparison still paid, because holding a raster next to a
vector serialisation of the same design is what made an unused `<filter>`
visible at all. Neither artefact alone shows it: the PNG looks right, and the
SVG renders right. Only the pair says the grain was never there.
