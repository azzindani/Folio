# Live sweep #20 — what happens when two calls arrive at once?

Nineteen passes asked what the engine does with **one** call. Every probe sent
a request and waited for the reply. But a model fires parallel tool calls
routinely, and Folio has **no locking anywhere in `src/mcp`** — every design
write is read-modify-write. So: what happens when two land on the same design?

## Almost always nothing, for a reason nobody wrote down

`readYAML` and `writeYAML` are `readFileSync`/`writeFileSync`. On a
single-threaded event loop, a read → mutate → write with no yield in between
**cannot** be interleaved by another request. Twenty concurrent updates to one
design, each on its own layer: **20 of 20 land.**

That is a real guarantee. It is also an accidental one — nothing declared it,
nothing checked it, and it holds only as long as every writer stays synchronous.

## One op does not stay synchronous

`shape` is the only design-writing op that is `async`, because `offsetPath` and
`outlineStroke` do `await import('polygon-clipping')`. That await sat between
the read and the write:

    128  const spec = readYAML(dPath);        ← reads the WHOLE design
    179  await outlineStroke(...)             ← yields the event loop
    192  await offsetPath(...)                ← yields the event loop
    208  writeYAML(dPath, spec);              ← writes back the line-128 document

Anything that landed in that window was overwritten by a document captured
before it.

| run | reported success | actually in the file |
|---|---|---|
| 20 updates + one cold `shape offset` | 20 | **18** |
| 20 updates, no shape op (control) | 20 | 20 |

`k2` and `k18` were told they were saved, and were not. The window is widest on
the first shape call after a restart, when the dynamic import is a real module
load rather than a cached promise.

## The fix

Move the async work ahead of the document read. `buildShapes` does the path
math and returns the raw `d` strings; only then is the design read, mutated and
written, with no yield in between. Two things fall out of doing it properly:

- style is taken from the **fresh** layer, so a concurrent restyle is respected
  instead of being overwritten with a colour the design no longer has;
- if the target layer is gone by the time the math finishes, the op refuses and
  writes nothing, rather than resurrecting it from a stale copy.

`atomic-design-write.test.ts` states the property for all 22 files that write
designs: **no `await` between reading a design and writing it back.** Reverted
against the old code it fails with `src/mcp/engine/shape-ops-op.ts:208`.

## The test was wrong before it was right

The first version of the concurrency test relied on `await import(...)` being
slow. That is true only while the module is cold — so it passed its first test
and **silently stopped racing at all** in the other four. Two of five failed for
reasons that had nothing to do with the bug.

Gating the async step explicitly made the race deterministic: the op parks
where it really yields, the concurrent write lands, then it is let through. All
five now fail against the old code and pass against the new.

**A timing-dependent test is not evidence.** If the thing under test is a race,
the test has to own the ordering.

## Also: my own test wrote into the repo

`src/renderer/mod.ts`, `src/export/mod.ts` and `src/engine/mod.ts` — three
one-line files — were sitting untracked in `src/`. The first version of pass
19's fingerprint test built its temp tree from a module-level `tmp` that was
still `''` in one describe block, so `path.join('', 'src', 'renderer', …)`
resolved into the working directory.

They were inside the fingerprinted directories, so the deployed container's
fingerprint reflected files that were not in git: `bce6d053d697dc33` with them,
`f5d4b75beb6f73f1` without. Harmless — one spurious cache invalidation — but
it means **a test that builds paths from a variable can write into the repo
when that variable is empty.** Removed.
