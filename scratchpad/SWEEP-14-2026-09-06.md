# Live sweep #14 — the fault found while tidying up

Pass 14 was not planned. Binning the pass-13 test project ran into it:

    manage_design {op:"delete", project_path:"…/sweep13"}
    -> The "path" property must be of type string, got undefined

That is a V8 internals message, not an answer. `delete` wants `design_path`;
nothing said so. The guard written three passes ago exists precisely to stop
this — so the question became **how much of the surface does it actually cover?**

## The measurement

Every op of all eight multiplexers, called with `op` alone, against the live
server. **15 of 71 still answered with internals.**

| tool | ops raw | needed |
|---|---|---|
| manage_design | 13 of 26 | list, inspect, rename, duplicate, move, delete, resume, get_spec, resize, tokens, lineage, restore, style_history |
| themes | 1 of 3 | list |
| tasks | 1 of 3 | list |
| edit_layer · templates · report · presentation · animation | 0 | — |

`manage_design` — the largest tool on the surface — had **no row in the table at
all**. Its thirteen design ops went straight to a path resolver.

## Why it read as covered

Its *asset* ops each hand-check their own arguments and name the missing one:

    asset_add     -> "project_path is required"      ← clean
    delete        -> The "path" property must be…    ← raw

Nine ops answering correctly is enough to make the tool look guarded from any
sample. The two `list` ops failed the same way for the opposite reason: both
were assumed to be argument-free menus. Both take `project_path`.

## The fix, and the door closed behind it

Each new row is the plain conjunction from that op's own published `req:` list,
so the check and the contract cannot drift. Where the requirement is an
either/or — `resize` wants width **and/or** height, `asset_add` wants `data`
**or** `source_path` — only the unconditional part is listed. A false rejection
would be worse than the crash it replaces.

The more useful half is the new test. A sample is how this survived thirteen
sweeps: nobody wrote the case, so nobody saw the crash. So the test stops
sampling — it reads the op lists straight out of `dispatch.ts` and fails if any
advertised op has neither a `PER_OP` row nor an exemption named with a reason.
It fails the other way too, if the table claims an op that no longer exists.
Verified by deleting one row: `expected [ 'lineage' ] to deeply equal []`.

## A second fault, from actually using the tool

Clearing the two items left for the user meant moving five loose designs into a
new project. Afterwards:

    manage_design {op:"list"}    -> 0 designs   (reads project.yaml)
    manage_design {op:"browse"}  -> 5 designs   (scans the disk)

`move` renamed the file and touched **neither** manifest. The source kept
advertising a path that resolves to nothing; the target held five designs it did
not list. `delete` was taught to maintain the manifest — its code even carries
the comment explaining why — but the row handling was written INLINE there
rather than shared, so the sibling that can break the same invariant never
learned it.

**When one op is taught to maintain an invariant, every op that can break it
needs the same lesson — and the way to make that stick is to extract the
maintenance, not to copy it.** Both ops now share `dropManifestRow` /
`addManifestRow`. The row is carried, not rebuilt, so a carousel marked `final`
does not arrive as a draft poster, and it is dropped only after the rename
succeeds so a failed move cannot erase the source row.

Repaired the five already-moved files through the fixed code path — out to a
staging project and back — rather than hand-editing YAML. `list` and `browse`
now both say 5.

## An instrument fixed, again

`mcall.sh` sliced the JSON reply at 2500 chars *before* parsing it, so five
perfectly good designs came back as `JSONDecodeError` and looked corrupt. Second
time in three passes that my own tool produced the finding — pass 12 was
`probe.sh` hiding a `findings` array. The durable copy now lives at
`scratchpad/mcall.sh`, parses first and trims for display, prints findings
before anything can push them off the end, and says so when it truncates.

24 faults, 18 commits. Thirteen of the fourteen passes went looking for a fault.
Pass 14 found both of its by *using* the thing — binning a test project, then
tidying five files. Neither needed a clever probe; they needed someone to
perform an ordinary chore end to end and check the result. That is the argument
for the structural test added here: the next gap should not have to wait for
someone to trip over it.
