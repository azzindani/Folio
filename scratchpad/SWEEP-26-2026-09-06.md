# Live sweep #26 — degenerate input

Twenty-five passes asked whether the engine does the right thing with input it
understands. This one sends input it does not: numbers that are not numbers,
zero and enormous geometry, the wrong type at every position.

**Most of it is already handled.** NaN, negative and zero sizes all come back
with a clear, actionable message. Six got through, and one of them is not
degenerate at all.

## The one that matters

Two ordinary verbose layers. No `z`. Nothing about this looks like an attack.

    add_layers      → success
    render_preview  → drew it
    seal_design     → sealed, clean, here is the share link
    export_design   → "Validation errors: Layer z-index is required"

The model builds it, previews it, seals it, hands the user the link — and the
export is refused. `z` is required by the schema, and **only export runs the
validator**.

Auditing the library: **5 real designs cannot be exported at all**, 4 of them
sealed and handed over. A re-seal now repairs 4 of the 5.

Missing `z` becomes **0, not the array index** — the renderer sorts by
`(a.z ?? 0)` with a stable sort, so 0 reproduces today's stacking exactly, while
an index would lift an unzoned layer above an explicit `z: 5` and silently
restack the design.

## The other five

| input | before |
|---|---|
| no `id` | unreachable by every op, and refuses the export |
| `id: 99` | stored as a NUMBER; every lookup compares `===` against a string, so `edit_layer` answers "Layer not found: 99" about a layer plainly in the file |
| `content: 7` on a text layer | renderer throws `undefined is not an object (evaluating 'value.length')`, draws a ⚠ placeholder, add_layers reports success |
| `layers: "nope"` | `layers` is TYPED `Layer[]`, so nothing checked it, and `"nope".length === 4` walked past the emptiness guard — the string BECAME the layer array: `layers.filter is not a function` |
| `layers: [null]` | `null is not an object (evaluating 'o.children')` |

The last one is mine, from pass 24. `stripNullLayers` has always carried the
comment *"before any pass reads `.id` off it"* — and sat **third** in the chain,
so every pass added above it inherited the hazard. **A guard placed after the
thing it guards protects nothing, and the next person to add a pass has no way
to know.** It now leads the chain, and the alias fold is null-safe on its own.

`layers` as a string is coerced leniently rather than refused outright — a
JSON-encoded array is recovered, exactly as `layers_shorthand` already does,
because that is the commonest way a model gets it wrong.

## Reported, not fixed

One design carries `type: "bg"`, which is not a layer type. `rect` is the
obvious guess and guessing is the thing §0.4 forbids: the engine assists, it
does not decide what the model meant.

Two things this pass says about the previous twenty-five. The engine is
genuinely well defended against input that is *obviously* wrong — every size
check fired correctly, first time. What it did not defend was input that looks
fine and is quietly incomplete, and the tell is always the same: **one surface
accepts what another refuses.** Preview drew a design export would not take;
seal blessed it; the validator that knew ran last and alone.

And a regression of my own, found four passes later by a probe I only wrote
because the user asked for one more sweep. **The value of the sweep is not the
bug you are hunting.**
