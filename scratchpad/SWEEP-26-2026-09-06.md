# Live sweep #26 — degenerate input

Twenty-five passes asked whether the engine does the right thing with input it
understands. This one sends input it does not: numbers that are not numbers,
zero and enormous geometry, the wrong type at every position.

**Most of it is already handled.** NaN, negative and zero sizes all come back
with a clear, actionable message. Six got through, and one of them is not
degenerate at all.

## The one that matters

Two ordinary verbose layers. No `z`. Nothing about this looks like an attack.

    add_layers      → success
    render_preview  → drew it
    seal_design     → sealed, clean, here is the share link
    export_design   → "Validation errors: Layer z-index is required"

The model builds it, previews it, seals it, hands the user the link — and the
export is refused. `z` is required by the schema, and **only export runs the
validator**.

Auditing the library: **5 real designs cannot be exported at all**, 4 of them
sealed and handed over. A re-seal now repairs 4 of the 5.

Missing `z` becomes **0, not the array index** — the renderer sorts by
`(a.z ?? 0)` with a stable sort, so 0 reproduces today's stacking exactly, while
an index would lift an unzoned layer above an explicit `z: 5` and silently
restack the design.

## The other five

| input | before |
|---|---|
| no `id` | unreachable by every op, and refuses the export |
| `id: 99` | stored as a NUMBER; every lookup compares `===` against a string, so `edit_layer` answers "Layer not found: 99" about a layer plainly in the file |
| `content: 7` on a text layer | renderer throws `undefined is not an object (evaluating 'value.length')`, draws a ⚠ placeholder, add_layers reports success |
| `layers: "nope"` | `layers` is TYPED `Layer[]`, so nothing checked it, and `"nope".length === 4` walked past the emptiness guard — the string BECAME the layer array: `layers.filter is not a function` |
| `layers: [null]` | `null is not an object (evaluating 'o.children')` |

The last one is mine, from pass 24. `stripNullLayers` has always carried the
comment *"before any pass reads `.id` off it"* — and sat **third** in the chain,
so every pass added above it inherited the hazard. **A guard placed after the
thing it guards protects nothing, and the next person to add a pass has no way
to know.** It now leads the chain, and the alias fold is null-safe on its own.

`layers` as a string is coerced leniently rather than refused outright — a
JSON-encoded array is recovered, exactly as `layers_shorthand` already does,
because that is the commonest way a model gets it wrong.

## Reported, not fixed

One design carries `type: "bg"`, which is not a layer type. `rect` is the
obvious guess and guessing is the thing §0.4 forbids: the engine assists, it
does not decide what the model meant.

## Coda — the motion-preview work, and what it cost

The four preview features (`649968a`, `614867d`) shipped with 4563 green unit
tests and a **broken editor**. CI caught it; vitest could not have.

Two faults, one symptom — the page loaded its chrome and drew no artwork:

1. `readonly motionPlayer = new MotionPlayer(this.state)` as a field
   initializer on `EditorAppBase`. Base-class field initializers run before the
   subclass constructor, and `this.state = new StateManager()` lives in the
   subclass constructor. The player captured `undefined` and kept it.

2. `StateManager.notify` ran its listeners in a bare loop. The toolbar's new
   play-button subscriber threw, the loop stopped, and **every listener
   registered after it — including the canvas — never heard the change.**

Fault 2 is the one that matters. Fault 1 was an ordinary mistake; fault 2 is
what turned an ordinary mistake into "Folio is down". Any panel could have
done this, at any point in the last twenty-six passes.

Worth noting: the codebase already knew the rule. `file-watcher.ts` isolates
its callbacks ("Callback errors must not break the watcher loop"), and
`motion-player.ts` isolates its own ("a bad listener must not stop playback").
`state.ts` — the one loop every panel in the editor hangs off — did not.
A house rule observed in the leaves and skipped at the root.

Same shape as the door faults, one level up: **the capability was right, the
place it was wired was wrong.** Here the wiring was a language rule about
initialization order and an unguarded `for` loop.

### The instrument lesson

Nine commissioning specs and four visual specs failed, and *not one of them
mentioned motion*. They timed out on a canvas SVG, a text layer, an asset in a
PNG. A failure list that points nowhere near the change is itself the signal:
it means something shared broke, not something local.

Two of the local reruns were my own noise, both from an incomplete environment
rather than the code:
- `npm run build` is `gen && tsc && vite build && build:assets`. I ran plain
  `vite build`, which **empties the outDir** — so the asset-explorer bundle
  vanished and five library-assets specs failed on a lazy chunk that was no
  longer on disk.
- `playwright.config.ts` uses `reuseExistingServer: !CI` on port 4173, which is
  the **deployed docker container**. Locally the visual suite was talking to
  production and getting the token gate. `PLAYWRIGHT_PORT=4399` and it passes.

Neither was a regression. Both looked exactly like one for a while.

## Live verification of the four features — five more faults

Deployed, then drove the real thing: raw JSON-RPC for `op:preview`, a headless
browser against the deployed editor for the other three. All four work. Getting
that answer cost five fixes, and **not one of them was findable from a unit
test**, because in every case the output looked fine.

| # | Fault | Why no test saw it |
|---|---|---|
| 1 | Filmstrip arrived with no timecodes | The strip's Resvg call was the only one in the file without `font:`. resvg DROPS text it cannot resolve. Dev machines have monospace fonts; the container does not. The test asserted the labels were in the SVG — they always were. |
| 2 | Linters could not read half the text | `content?.value` written inline at five call sites. A bare scalar and RICH TEXT (words in `spans`, no `value`) both read as `''`. |
| 3 | `create_design` ate a `layers` argument | Not in the schema, not rejected either. Success + a link to a blank canvas. |
| 4 | Trails drew nothing mid-playback | My own fix from two commits earlier. A freeze can only HOLD a trail; it cannot make one. |
| 5 | Timecode read `0.163.799999976s` | `ms % 1000` padded to three chars. Only ever fed integers until the player fed it rAF times. |

Fault 2 is the one with teeth. The false "this slot is EMPTY" note is noise —
it tells a model to rewrite copy that is already written. The silent half is
the damage: `measureTextLayer` bails on empty text, so those layers got **no
overflow and no autofit check**, and the low-contrast pass skipped them
outright. Invisible text shipped unflagged. §0.4 says spatial correctness is
the engine's job, and the engine was not doing it on text it could not read.
4592 tests pass after widening it — nothing depended on the blindness.

Fault 4 is worth keeping for the shape of the mistake, not the mistake. I saw
the trail crawl during playback and stopped the repaint. That is treating the
symptom: the trail should never have been *measured from the pose*. Deriving
it from the authored layers is stable by construction, works mid-playback, and
deleted the freeze rather than fixing it. **When a fix is a guard against a
symptom, the bug is usually upstream of the guard.**

### On instruments, again

My first browser probe reported "pressing play does not animate the layer".
It was measuring `[data-layer-id="card"]` — which matches the **layer-panel
row** as well as the SVG element, and the panel row was what it found.
Playback had been correct the whole time (432→458px, opacity 0→1). Scoping the
query to `.canvas-area svg` turned a FAIL into a PASS with no code change.

Two instrument errors in a row now (this, and the 4173 port collision earlier).
Both had the same tell: **a failure that makes no sense given what changed.**
That is a reason to doubt the probe before the code.

And fault 5 exists because I looked at the SCREENSHOT the probe saved rather
than only its PASS/FAIL lines. Every assertion passed. The panel was visibly
broken in the image.

### Instrument error #3, and the fix for it

`create_design` looked like it was still dropping layers in silence on the
deployed server — the warning I had just written and tested was nowhere in the
reply. It was there the whole time. `scratchpad/mcall.sh` lists `progress` in
its `drop` set, so the helper I use to inspect the wire was deleting the exact
field that carries warnings.

Three instrument errors this session, all with the same tell — **a result that
contradicts something already verified**:

| Instrument | Lied by | Tell |
|---|---|---|
| `vite build` alone | emptying outDir, killing the asset bundle | 5 specs failed on a lazy chunk unrelated to the change |
| playwright port 4173 | reusing the deployed container | an auth gate in a suite that never authenticates |
| `mcall.sh` | dropping `progress` | a warning missing that a unit test proved present |

The helper now prints every non-`ok` progress item. An inspection tool that
hides warnings is worse than no tool: it converts "there is a problem" into
"there is no problem".

## Coda 2 — "it's just my test" was the wrong place to stop

The `type: "bg"` layer in `air-cargo-board-deck-–-carousel` came from a user
test and the design does not matter. What mattered was the question it raised:
**does the engine say anything when a layer type is unknown?**

It says a great deal, in exactly one place. `validateDesignSpec` produces
`pages[0].layers[1].type  Unknown layer type: "bg"` — the field, the path, the
value — and it was called from ONE site in the whole MCP surface:
`export_design`, at the very last step. `diagnose_design` assembled findings
from four sources and the schema was not among them. `seal_design`, which now
refuses a design carrying unresolved errors, asked those same four.

So a model could diagnose clean, seal, and hand over the share link on a design
whose own validator knew precisely what was broken. The door fault again, at
the level of a whole pass: **the right capability, wired to one door.**

Then the fix did not show up live, and the second fault was better than the
first. `diagnose` caps its findings at 40 and kept whichever 40 were gathered
FIRST — so the schema pass, newly appended last, was cut wholesale. And this
design has 60 off-canvas errors, which crowded out every other KIND of problem
regardless of order.

That cap was quietly turning a complete diagnosis into a queue: fix sixty
off-canvas layers, re-diagnose, meet the next problem, repeat. `rankForDisplay`
now shows one of each code before a second of any, errors first. Same design,
after: the schema error sits second in the list.

Blast radius measured before shipping, on 432 live designs — 7 carry schema
errors, 3 already sealed, all of which would fail export today. The validator's
*warnings* are 9,934 findings on 117 designs and almost all are "Duplicate
z-index", harmless because the renderer sorts stably. Errors only, and the
corpus is why.

**A cap that drops findings is a policy about what matters, not an
optimisation.** This one had never been given a policy.
