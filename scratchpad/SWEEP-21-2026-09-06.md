# Live sweep #21 — is a design's export the same file twice?

Pass 19 compared two artefacts that must agree. Pass 20 compared the same
system at two moments. The comparison left is the last one available: a thing
against **itself**.

Export one unchanged design three times, forcing past the cache:

| run | md5 | generated ids |
|---|---|---|
| 1 | `d5776eb2…` | `lg-1  noise-2  noise-3` |
| 2 | `ad508b0f…` | `lg-4  noise-5  noise-6` |
| 3 | `9a6146f9…` | `lg-7  noise-8  noise-9` |

Three files. Identical pixels. The only diff between run1 and run2 is the ids.

## The counter, and the reset nobody called

`svg-utils.ts` minted def ids from a module-level counter:

    let defIdCounter = 0;
    export function uniqueDefId(prefix) { return `${prefix}-${++defIdCounter}`; }
    export function resetDefIdCounter() { defIdCounter = 0; }

The reset existed. It was exported from the renderer's public `index.ts`. And
**every one of its callers was a test file** — nine of them, each calling it in
`beforeEach` so their own ids were stable.

That is the sharpest version of this session's recurring fault. The usual door
fault is a capability behind the wrong entry point. Here the tests didn't just
fail to notice — they *manufactured* the determinism they were asserting.
`svg-utils.test.ts` stated the defect as the contract:

    it('increments counter on each call', () => {
      expect(id1).toBe('grad-1');
      expect(id2).toBe('grad-2');
    });

4,400 tests, and the one closest to the bug was pinning it in place.

## The obvious fix would have been worse

Calling the reset per render looks right and is not.
`presentation-assembler.ts` does `pages.map(renderSlide).join('\n')` — every
slide's `<svg>` in ONE html document. Reset per render and every slide restarts
at `lg-1`; `url(#lg-1)` resolves to the first match in the document, so slide 5
quietly paints with slide 1's gradient. A visible, cross-page colour bleed.

**The unused function wasn't merely unwired — it was unusable where it looked
like it belonged.** An existing test even guarded the hazard, with its mechanism
written in the comment: `expect(idOf(a)).not.toBe(idOf(b)); // monotonic
counter, no per-render reset`.

## Content-derived ids

`defIdFor(prefix, content)` hashes what the def contains (FNV-1a — not node's
`crypto`, because this module also runs in the browser). Then:

- the same design always renders the same ids ✓
- two slides sharing a gradient share an id whose **definition is byte
  identical**, so resolving to either is correct ✓
- two *different* fills — the only collision that could paint wrongly — still
  get different ids ✓
- `appendDefOnce` drops the duplicate, so a poster whose every card uses one
  accent gradient defines it once instead of once per card

The guarantee in the cross-SVG test changes shape: not "ids never collide" but
**"a shared id always means an identical definition"**. That is the sharper
claim, and it is the one that makes the presentation assembler safe.

## Who already knew

`preview-diff.ts` did. It carries `canonicalSVG`, which renumbers ids before
hashing, and a comment describing this exact drift — because `changed_only`
otherwise reported every page as changed on every call. One consumer had been
told and worked around it locally; the cause stayed put. Meanwhile
`export-receipt`'s key claims "identical inputs through identical code →
identical bytes", which was simply false for any design with a gradient.
