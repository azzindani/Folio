# Live sweep #22 — is the engine's own output a fixed point?

Pass 19 compared two artefacts, 20 compared two moments, 21 compared an input
against itself. This one feeds the engine's **output back in**: a normalisation
that does not converge is silently fighting itself.

Most of it converges, and that is worth recording as much as the failure:

| probe | result |
|---|---|
| `heal` on a messy poster | 1 round, `fixed: []`, stops because nothing changed |
| add one layer to a finished design | existing layers untouched |
| `resize` to the same dimensions | no-op, with an honest "Already that size" note |
| `patch_spec` with a field's current value | `changed: []`, byte-identical |
| `patch_spec` A → B → A | **did not return to A** |

The last one is the finding. And the shape of it mattered: the *second* round
trip was clean. That is what said the drift was in the FIRST expansion, not in
the edit — `A` was never a fixed point, `A'` was.

## What differed

`patch_spec` re-expands a preset through the same expander `add_layers` uses,
and the comment there claims it runs "in the same engine context the original
was built in". It does not. `add_layers` expands and *then*:

- fits the result to the page — `honorPosterRatio`, for a poster on a
  deliberate standard ratio (1080×1350 is 4:5);
- re-lights its text — `fixInvisibleText`, `fixCapsTracking`.

Re-expansion skipped all of it. Measured on a 1080×1350 poster, after editing
**one field** of a `sections` preset:

    container + 3 background layers   height 1350  ->  972
    black rows at the bottom          378 = 28.0% of the page
    accent text                       #613810  ->  #F28C28  (orange on cream)
    ALL-CAPS tracking                 1  ->  0.5

The 972 is the preset's natural content height. `patch_spec` is the *recommended*
way to evolve a preset — "one call instead of thirty edits".

## Two things the fix had to get right

**Run over the whole surface, not the rebuilt layer.** My first attempt passed
`[rebuilt]` to `fixInvisibleText`. Given only the group, it cannot see what is
behind the text and re-lit it **white on a cream page** — a worse bug than the
one being fixed.

**Do not resize the user's canvas.** `honorPosterRatio` also grows the document
to contain overflow, and `add_layers` accepts that. An edit to one field must
not silently reshape the page, so the fit runs on a clone and is kept only when
it lands on the canvas the design already has.

I also spent three attempts fixing this at the wrong layer — pre-expansion
shorthand passes (`fillBleedPresetDims`, `fillFlowPresetsToPage`) — before
reading far enough to find `fillFlowPresetsToPage` is gated on paged designs
("Posters … are untouched — they keep content-sizing + the centering pass").
The pre-expansion attempt also polluted the stored `_spec` with a derived `pos`
and leaked the internal `__fillPage` marker into `_spec_env`. **The stored spec
records what the model wrote; anything the engine derives must not land in it.**

## Reported, not fixed: the art direction re-rolls on every edit

Patching the kicker five times, watching the background:

    #FAFAFA -> #1A1A1A -> #F6EFE2 -> #15202B -> #E9F6EE

Light, dark, light, dark. It does not converge, and **it predates this fix** —
verified by reverting the change and re-running.

The cause is deliberate: `seededDefaults(r, [title, subtitle, kicker, …])`
seeds the mood from the copy, so a preset whose style the model dropped still
gets a curated art direction. Content-seeding at CREATION is the intent. But it
means editing any text field re-rolls the whole palette: fix a typo in the
kicker, get a different poster.

`ENV_KEYS` already stamps `__variant` and `__deckseed` so those survive
re-expansion — the same pattern would fix this, by recording the chosen mood at
creation and reusing it. That is a change to the aesthetic layer with reach
across every preset, and pass 17's lesson applies: *an inconsistency can be
load-bearing; report it rather than "fixing" it blind.* So it is written down
here with the evidence, not shipped.

## The disk filled mid-edit and truncated a source file

`/` hit 100% (193G) during this pass — 24GB of it docker build cache from the
session's repeated deploys. A `python` rewrite of `engine-spec-tools.ts` was
interrupted and left the file **0 bytes**; `tsc` then reported errors in four
unrelated files, which is what surfaced it.

Restored from HEAD and redone. Every subsequent edit writes to `<file>.new`,
fsyncs, then `os.replace`s — an atomic rename cannot leave a half-written
source. **A tool that rewrites a file in place turns a full disk into data
loss.**

its output back next to what `add_layers` would have produced shows the two
paths disagree.
